<role>

<context>
`lib/oggOpusMuxer.js` turns Opus RTP payloads into Ogg pages for the H.264
fallback relay. Line coverage is high (95.83%) but **branch coverage is 48.39%**
— the file is well exercised on one path and barely on the others. Two specific
branch clusters have no assertion.

Verified facts you do not need to rediscover:

- Uncovered ranges from a full-suite coverage run: `33-35` and `74-76`.
- Lines 33-35 are inside `opusPacketDurationSamples()`: the TOC frame-code 3
  path, where the frame count comes from `packet[1] & 0x3f`, plus the
  `packet.length < 2` guard that returns `0`. Frame codes 0, 1 and 2 are already
  exercised; code 3 is not.
- Lines 74-76 are inside `OggOpusMuxer._page()`: the `while (remaining >= 255)`
  lacing loop that splits a payload across multiple Ogg segments, and the
  `segments.length > 255` throw (`'Opus packet is too large for one Ogg page.'`).
  Existing tests only push payloads under 255 bytes, so the loop body never runs.
- `opusPacketDurationSamples` is **exported directly** from the module
  (`module.exports` at line 139 exports `OggOpusMuxer`, `extractOpusRtp`,
  `oggCrc`, `opusPacketDurationSamples`). Test it as a pure function — no RTP
  wrapper needed.
- `_page` is private, but reachable through `OggOpusMuxer#pushRtp(packet)` with
  a large payload. `pushRtp` returns `null` for anything it rejects, so a
  returned Buffer is itself proof the page was built.
- `pushRtp` returns a page only when the granule advances: see line 133,
  `if (nextGranule <= this.granule) return null`. Advance the RTP timestamp
  between pushes or you will get `null` and misread it as a failure.

Out of scope, deliberately: the "32-bit RTP timestamp wraparound" scenario from
`testing/gap_03_h264_fmp4_relay.md`. `pushRtp` currently drops every packet
after a wrap, permanently. Whether that should stall, resync, or reset the
base granule is a product decision with no stated answer, and it is not a test
gap. Do not write a test that pins the current stall as correct.
</context>

<task>
Extend `tests/oggOpusMuxer.test.js` to cover Opus TOC frame-code 3 and the
multi-segment Ogg lacing path. When this is done, branch coverage of the module
is materially above 48.39% and both clusters have assertions that would fail if
the framing arithmetic changed.
</task>

<steps>
Order is not load-bearing.

- `opusPacketDurationSamples`, frame code 3: build a one-byte-TOC-plus-count
  packet where `packet[0] & 3 === 3` and `packet[1] & 0x3f` is a frame count,
  and assert the returned sample count equals `frameSamples * frameCount` for
  the config you chose. Pick a config and count whose product stays at or below
  5760, since line 38 returns `0` above that.
- Same function, the ceiling: build a code-3 packet whose frame count pushes the
  duration past 5760 samples and assert it returns `0`.
- Same function, the truncation guard: a code-3 packet exactly one byte long
  must return `0` (line 34) rather than reading past the end.
- Multi-segment lacing: push an RTP packet whose Opus payload is at least 255
  bytes — 600 is a convenient size — and assert the returned page's segment
  table. Read the segment count from byte 26 of the Ogg header and the lacing
  values from byte 27 onward; assert they sum to the payload length and that all
  but the last are 255. Assert the header still starts with `OggS`.
- Assert a payload just under and just over the 255 boundary produce 1 and 2
  segments respectively, so the loop's edge is pinned rather than just its
  middle.
</steps>

<constraints>

- Do not attempt the `segments.length > 255` throw unless you can reach it with a
  payload the muxer would really accept; if the RTP path caps payload size

- Do not weaken, skip, or delete an existing test.

- Match the surrounding style.
</constraints>
