<role>

<context>
`lib/https.js` generates and caches the self-signed TLS certificate Nextra serves
when HTTPS is enabled. `shouldRegenerateExistingCert()` decides whether a cert
already on disk still matches the configured security settings, or must be
thrown away and regenerated. If it wrongly returns `false`, an operator keeps
serving a certificate whose SAN no longer covers the address they browse to.

Verified facts you do not need to rediscover:

- A full-suite coverage run (`node --test --experimental-test-coverage`) puts
  `lib/https.js` at **16.09% lines and 0.00% functions** — the lowest function
  coverage of any module in `lib/`. Uncovered ranges are `7-18 20-41 47-85`,
  which is every line of every function.
- No file in `tests/` imports `lib/https.js`. There is no `tests/https.test.js`.
- `lib/https.js` exports **only** `getOrCreateCert`. `shouldRegenerateExistingCert`
  and `getDesiredAltNames` are module-private. Do not export them — drive both
  through `getOrCreateCert()`, which is the real entry point and gives you the
  disk-cache branches at lines 47-85 for free.
- `config` (`config.js`) is a plain mutable object exported at line 460; it is
  not frozen. The established pattern in this repo is to save the previous
  value, assign, and restore in a `finally`. See
  `tests/rooms.test.js:138-170`. Tests that mutate shared config must be
  declared `{ concurrency: false }` so they do not race the rest of the suite.
- The relevant config keys are `HTTPS_CERT_DIR` (default `./certs`),
  `HTTPS_INCLUDE_LAN_IP_IN_CERT` (default `false`), and `LAN_IP`.
- `selfsigned` is already a production dependency (`package.json`). Use it to
  build fixture certificates. Do not add a dependency.
- `getOrCreateCert` writes `server.crt` and `server.key` into
  `config.HTTPS_CERT_DIR`. Point that at a `fs.mkdtempSync` directory per test
  and remove it afterwards. Never let a test write into the repo's `certs/`.
</context>

<task>
Add `tests/https.test.js` so every branch of the certificate-regeneration
decision is asserted through the public `getOrCreateCert()` entry point. When
this is done, `lib/https.js` function coverage is above 0% and each documented
regeneration trigger has a test that fails if that trigger stops working.
</task>

<steps>
Order is not load-bearing; each case is independent.

- Build a fixture helper that generates a cert with a chosen SAN set via
  `selfsigned.generate`, and writes it as `server.crt` / `server.key` into a
  temp `HTTPS_CERT_DIR`.
- Assert a cert whose PEM is unparseable garbage is regenerated (the `catch`
  at lines 24-26 returns `true`). Assert the returned cert differs from what
  was on disk.
- Assert a cert missing `DNS:localhost` is regenerated.
- Assert a cert missing `IP Address:127.0.0.1` is regenerated.
- With `HTTPS_INCLUDE_LAN_IP_IN_CERT = true` and `LAN_IP` set to a non-loopback
  address: assert a cert lacking that IP is regenerated, and a cert containing
  it is reused unchanged (returned PEM is byte-identical to the file).
- With `HTTPS_INCLUDE_LAN_IP_IN_CERT = true` and `LAN_IP` set to `127.0.0.1`:
  assert the cert is reused, covering the early `return false` at line 36.
- With `HTTPS_INCLUDE_LAN_IP_IN_CERT = false`: assert a cert carrying any
  non-loopback IP is regenerated (line 39).
- Assert the generation path when the directory is empty: `getOrCreateCert()`
  creates both files, and the generated cert's SAN contains `DNS:localhost` and
  `IP Address:127.0.0.1`. Use `new X509Certificate(...).subjectAltName` to read
  it back rather than asserting on raw PEM bytes.
</steps>

<constraints>
- Scope: add one test file. Change no source file.
- Assert the *decision*, not the implementation. Check "was the cert on disk
  replaced" by comparing PEM content, not by spying on `fs` calls — a spy would
  pass even if the regeneration logic inverted.
- Every test that assigns to `config` restores the previous value in a `finally`
  and is declared `{ concurrency: false }`. Leaking config state into the rest
  of the suite is the most likely way this card breaks unrelated tests.
- Remove every temp directory the test creates, including on failure.
- Do not weaken, skip, or delete an existing test.
- Match the surrounding style: CommonJS `require`, `node:test`,
  `node:assert/strict`, 4-space indent.
</constraints>
