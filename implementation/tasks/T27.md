# T27 — Regenerate cached TLS credentials that do not exactly match the configured endpoint

<model>
Model: `claude-sonnet-5`
Effort: `high`
Card: T27 in `../KANBAN.md`
Depends on: none
</model>

<role>
You are a Node.js engineer fixing validation at a local TLS credential boundary.
You write the two failing regressions first, then make the smallest change that
causes an unusable cached certificate/key pair to be regenerated.
</role>

<context>
`lib/https.js` generates and caches the self-signed certificate Nextra serves
when local HTTPS is enabled. The cache is disposable: if either credential is
unusable or no longer represents the exact configured SAN set, regeneration is
safer than allowing server startup to fail or serving a misleading certificate.

Two defects are reproduced against the current source:

- `shouldRegenerateExistingCert()` uses substring checks. With
  `HTTPS_INCLUDE_LAN_IP_IN_CERT=true` and `LAN_IP=127.0.0.10`, a certificate
  whose only SANs are `DNS:localhost.example.com` and
  `IP Address:127.0.0.10` is reused. It contains neither exact required identity
  (`localhost` and `127.0.0.1`). `X509Certificate#checkHost` with
  `{ subject: 'never' }` and `X509Certificate#checkIP` distinguish the exact
  names on the repository's supported Node version.
- A valid localhost certificate paired with a different generated private key
  is also reused. `tls.createSecureContext({ cert, key })` then throws
  `ERR_OSSL_X509_KEY_VALUES_MISMATCH`, so `server.js` cannot start HTTPS.

Verified surrounding facts:

- `lib/https.js` exports only `getOrCreateCert()`. Keep the validation helpers
  private and drive every case through that public entry point.
- `config` is a mutable singleton. Save, assign, and restore every changed key
  in `finally`, and declare config-mutating tests `{ concurrency: false }`.
- `selfsigned` is already a production dependency and can generate all fixture
  certificates and keys. Add no dependency.
- `getOrCreateCert()` writes `server.crt` and `server.key`; every test must point
  `HTTPS_CERT_DIR` at its own `fs.mkdtempSync` directory outside the repository.
- Full Node-suite coverage currently reports `lib/https.js` at 16.09% lines and
  0.00% functions because no tracked test imports it.
</context>

<files>

<task>
Make `getOrCreateCert()` reuse cached credentials only when the certificate has
the exact required SAN identities and the private key is usable with that
certificate. Preserve the existing SAN policy and file names; regenerate the
same local self-signed credential whenever validation fails.
</task>

<steps>
The first three steps are order-sensitive because both defects must be proven
against the unmodified source before the fix is accepted.

1. Create the fixture helpers and add only these two regression tests:
   - a certificate containing `DNS:localhost.example.com` and
     `IP Address:127.0.0.10`, with LAN inclusion enabled for `127.0.0.10`, is
     replaced rather than reused;
   - an exact-valid localhost certificate paired with another certificate's
     private key is replaced, and the returned pair is accepted by
     `tls.createSecureContext()`.
2. Run `node --test tests/https.test.js` and record both failures against the
   current source. If either passes, stop under `<escalate_if>`.
3. Change the private cache decision in `lib/https.js`:
   - require an exact DNS SAN for `localhost`; do not allow Common Name fallback;
   - require an exact IP SAN for `127.0.0.1`;
   - when LAN inclusion is enabled for a non-loopback `LAN_IP`, require that
     exact IP SAN;
   - when LAN inclusion is disabled, retain the current rule that an additional
     non-loopback IPv4 SAN causes regeneration;
   - attempt `tls.createSecureContext({ cert, key })` and regenerate on any
     certificate parse, private-key parse, or key-mismatch error.
   Pass the cached key into the private decision; do not export a helper.
4. Re-run the two regressions and confirm both pass.
5. Complete `tests/https.test.js` with independent cases for:
   - an empty directory generates both files and exact localhost/loopback SANs;
   - unparseable certificate PEM regenerates;
   - unparseable private-key PEM regenerates;
   - missing exact `DNS:localhost` regenerates;
   - missing exact `IP Address:127.0.0.1` regenerates;
   - LAN inclusion with a non-loopback IP regenerates when missing and reuses
     byte-identically when present;
   - LAN inclusion with `LAN_IP=127.0.0.1` reuses an exact-valid pair;
   - LAN inclusion disabled regenerates a certificate carrying another IPv4 SAN;
   - an exact-valid certificate/key pair is reused byte-identically.
</steps>

<constraints>
- Scope: change only `lib/https.js` and create `tests/https.test.js`.
- Keep `getOrCreateCert()` as the only export. A private validation detail is not
  a public API merely because it needs coverage.
- Assert replacement/reuse by comparing returned and on-disk PEM bytes. Do not
  spy on `fs`; a write spy does not prove the resulting credentials are usable.
- Use `tls.createSecureContext()` as the key-pair oracle. Do not compare public
  keys manually or add a cryptography dependency.
- Every test restores config and removes its exact temporary directory in
  `finally`, including on assertion failure.
- Do not write under the repository's `certs/` directory.
- Do not weaken, skip, or delete an existing test.
- Match the surrounding CommonJS, `node:test`, `node:assert/strict`, and
  four-space-indentation style.
</constraints>
