# T42 — Replace an existing WHEP ICE-disconnect reaper before scheduling another

<role>
You are a Node.js lifecycle engineer fixing one deterministic timeout-ownership
bug. Prove both consequences with fake-time red tests, then add the smallest

</role>

<context>
Each successful WHEP session stores one `iceDisconnectTimer`. On ICE
`disconnected`, `lib/whepRoutes.js` currently assigns a new 30-second timeout
without clearing a timeout already stored in that field. The old handle becomes
unreachable but remains live.

Two failures are reproduced with Node's mocked `setTimeout` clock:

- If `disconnected` occurs at 0ms and again at 10,000ms, the session closes at
  30,000ms instead of resetting its deadline to 40,000ms.
- If `connected` follows the second signal, recovery clears only the second
  timeout; the orphaned first timeout still closes the recovered session.

The intended single-signal behavior is clear: one disconnect starts a 30-second
grace period, and connected/completed cancels it. Repeating the non-terminal
signal must replace that grace period, not create an ownerless reaper.

Use `t.mock.timers.enable({ apis: ['setTimeout'] })` and `tick(ms)`. Start the
HTTP listener before enabling timers. T40 owns other lifecycle cases in a
different test file.
</context>
