# T29 — Reject fMP4 boxes that declare a size smaller than their header

<model>
Model: `claude-sonnet-5`
Effort: `high`
Card: T29 in `../KANBAN.md`
Depends on: none
</model>

<role>
You are a Node.js engineer working on a binary stream parser that sits on a
trust boundary. You write the failing test first, make the smallest fix that
turns it green, and you do not touch parser behavior the test does not describe.
</role>

<context>
`lib/fmp4Parser.js` incrementally parses FFmpeg's stdout into an init segment
and `moof`+`mdat` fragments. It is a trust boundary: its input is the byte
stream of a child process fed by remote broadcaster media, so a malformed box
must fail closed with a diagnostic an operator can act on.

`_parseBoxes()` (lines 63-125) validates two of the three ways a box size can be
invalid. It rejects `boxSize === 0` (line 70) and `boxSize > MAX_BOX_SIZE`
(line 78). It never checks that `boxSize` is at least the 8-byte header it just
read. A box declaring size 4 is accepted, `_readOffset` advances by 4 instead of
8, and the parser desynchronises onto the box's own type field.

This was reproduced by hand against the current code. Feeding a valid init
segment, then an 8-byte buffer whose size field is `4` and whose type is
`styp`, produces:

```
emitted error: MP4 box size 1937013104 exceeds limit 134217728
```

`1937013104` is `0x73747970` — the ASCII bytes `styp` being read as a length.
The stream is discarded (correct outcome, reached by accident) and the operator
is handed a nonsense number instead of the real fault. Every subsequent byte on
that stream is dropped.

The fix is already decided, and the codebase already contains the rule:
`_readBoxHeader()` at line 189 — the helper used for the nested `moov`/`moof`
scans — rejects exactly this case with `if (size < headerSize || (offset + size)
> end) return null;`. `_parseBoxes` is the inconsistent one. Bring it in line.

Also verified: `tests/fmp4Parser.test.js` currently contains **exactly one
test**, covering video-track tagging. Full-suite coverage of `lib/fmp4Parser.js`
is 75.15% lines, 53.85% branches.
</context>

<task>
Make `_parseBoxes` reject a box whose declared size is smaller than its header,
with the same rule `_readBoxHeader` already applies, and emit an error naming
the actual bad size. Extend the parser's test file to cover that case and the
other malformed-box paths that currently have no assertion.
</task>

<steps>
Order is load-bearing: the test must fail before the fix, or you have not
demonstrated the bug.

1. Add a test feeding a valid init segment, then a box declaring size 4 with
   type `styp`. Assert the emitted error message names the offending size (`4`)
   and not a value derived from misreading later bytes. Run it and confirm it
   fails against the current code — quote the failure in your report.
2. Add the guard to `_parseBoxes`. It belongs with the sibling size checks, after
   the `boxSize === 0` branch, and must run before `boxSize === 1` is
   interpreted as an extended-size marker — `1` is a valid marker, not an
   undersized box, so ordering here is what keeps the extended-size path working.
   Follow the existing pattern in that function: emit an `error`, reset
   `_bufferLength` and `_readOffset` to 0, and `break`.
3. Re-run and confirm the new test passes and the pre-existing test still passes.
4. Add the remaining malformed-input cases, all of which should pass without
   further source changes:
   - `boxSize === 0` emits the "extends to EOF" error (line 71).
   - An extended (`size === 1`) box whose 64-bit size exceeds `MAX_BOX_SIZE`
     emits the extended-size error (line 93).
   - A `moof` arriving while a previous `moof` is still unmatched emits
     "Received moof without preceding mdat" and drops the incomplete fragment
     (line 143).
   - An `mdat` with no preceding `moof` emits "mdat received without preceding
     moof" and emits no `fragment` (line 155).
5. Assert that after each malformed input the parser is still usable: feed a
   well-formed `moof`+`mdat` pair afterwards and assert a `fragment` is emitted.
   Failing closed must not mean failing permanently.
</steps>
