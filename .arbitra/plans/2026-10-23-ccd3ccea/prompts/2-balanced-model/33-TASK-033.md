<goal>
Derive the WHIP remote DTLS role (passed to transport.connect) and the local a=setup emitted in the WHIP answer from one decision on the offer's setup attribute. Mapping: passive offer -> remote role 'server' and answer a=setup:active. active, actpass or absent -> remote role 'client' and answer a=setup:passive. The two values can then never contradict each other.

This matters because it fixes:
- DTLS role inverted for non-actpass setup attributes in WHIP ingest (medium)
  parseDtlsParameters maps remote section.setup === 'active' to role: 'server'. In mediasoup DtlsParameters, role designates the remote peer's DTLS role. When a client advertises setup:active (meaning the client is active/client), marking remote role as server while the server answer declares a=setup:passive creates a role mismatch where both sides expect the other to listen or initiate, breaking DTLS handshake establishment.
</goal>
