# TASK-002 · Correct H.264 frame-integrity attribution on marker loss and bound reassembly memory

<goal>
In H264Depacketizer.pushFrames, attribute a sequence gap to the frame that actually lost packets. Bound FU-A and access-unit accumulation by bytes and fragment count.

This matters because it fixes:
- RTP sequence gap detection occurs after frame emission on timestamp transition (high)
  In H264Depacketizer.pushFrames, when an RTP packet carrying the marker bit is dropped, frame completion is triggered by receiving a packet with a new timestamp. However, _emitFrame is invoked before checking whether sequence numbers advanced discontinuously. As a result, the damaged frame that suffered packet loss is emitted with intact: true, and the subsequent intact frame is mistakenly flagged with intact: false.
- H.264 reassembly has no aggregate memory limit (high)
  <quotes> this._fuBuffer.push(Buffer.from(fragment)); this._frameChunks.push(annexb); </quotes> Neither fragmented-NAL assembly nor access-unit assembly has a byte, packet or time limit. Sequential FU-A continuation packets with a fixed timestamp/SSRC and no end marker keep growing _fuBuffer. Complete NAL packets with a fixed timestamp and no RTP marker similarly keep growing _frameChunks.
</goal>

<steps>
1. Compute the gap (missing = (sequence - expected) & 0xffff) before the timestamp-boundary emit.
2. If the timestamp changed and a frame is pending (no marker seen), the pending frame lost its tail. Mark it not intact, then emit it.
3. Mark the new frame not intact only when more than one packet is missing at an unterminated transition (section-03922085d60db4bdcd8f9389/Q-005 default), or when the previous frame was already closed by a marker.
4. A gap with no timestamp change still damages the current frame.
5. Track running byte and fragment counters for the FU buffer and the access-unit buffer. When a limit is exceeded, drop the buffer, set _frameIntact=false, and skip further packets of that timestamp until the next boundary.
6. Make the limits constructor options. Defaults follow section-03922085d60db4bdcd8f9389/Q-002 (8 MiB NAL, 16 MiB access unit, plus a fragment-count cap).
</steps>
