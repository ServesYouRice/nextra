# TASK-013 · Make the host send path race-safe: create-send-transport post-await check and produce replacement

Suggested model: a balanced model (such as Claude Sonnet), effort high. Why: Concurrency is involved: async interleavings between duplicate requests and host reclaim; State coupling: producer close triggers existing close/transportclose handlers and viewer producer-closed notifications; There is a reference implementation in the same file: the create-recv-transport 'raced' check; Blast radius is medium: the host media path for every browser room

You are a careful senior engineer making one change in this repository. Read the material below before you edit anything, keep to the constraints, and stop and ask if something does not match what this prompt says.

<goal>
Ensure overlapping create-send-transport calls never orphan a host transport, transports created for a socket that left or lost host status are closed, and a same-kind produce closes the producer it supersedes.

This matters because it fixes:
- Transport creation handlers do not re-check state after the await; overlapping create-send-transport calls leak host transports (medium)
  create-send-transport closes the previous host transport, awaits createSocketWebRtcTransport, and then assigns room.hostTransport without checking what is there now. If two calls overlap (for example a client retry after a timeout; the join-room comment says socketRequest retries), both run the close step before either assigns. The first new transport is then overwritten without ever being closed. create-recv-transport handles this exact race with its raced check, but the host path does not. Neither handler checks after the await that the socket is still connected or still in this room, so a transport created for a socket that left mid-await is stored on a stale entry.
- Repeated produce requests leave superseded producers open (medium)
  <quotes> const producer = await room.hostTransport.produce({ kind, rtpParameters, appData }); if (kind === 'video') room.producer = producer; if (kind === 'audio') room.audioProducer = producer; </quotes> A successful produce request overwrites the room's single producer slot for that media kind without rejecting or closing an existing producer. Repeated same-kind requests therefore leave older producers alive on the send transport while losing their room-level references.
</goal>
