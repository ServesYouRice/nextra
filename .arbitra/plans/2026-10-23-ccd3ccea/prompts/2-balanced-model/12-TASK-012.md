# TASK-012 · Limit each viewer to one live consumer per producer in consume

Suggested model: a balanced model (such as Claude Sonnet), effort high. Why: Concurrency is involved: two awaits (recvTransport.consume and applyConsumerPriority) open interleaving windows; Domain knowledge needed: mediasoup consumer close and event semantics (observer close vs transportclose/producerclose); Blast radius is medium: it affects every SFU viewer, and a wrong dedupe could close a viewer's only consumer; Verification is deterministic with fake transports

You are a careful senior engineer making one change in this repository. Read the material below before you edit anything, keep to the constraints, and stop and ask if something does not match what this prompt says.

<goal>
Prevent egress amplification by ensuring a viewer's receive transport holds at most one live consumer per room producer, including under overlapping consume requests, by closing superseded consumers.

This matters because it fixes:
- consume lets one viewer create unlimited consumers of the same producer (egress amplification) (high)
  The consume handler checks three things: the producerId belongs to the room, the router can consume it, and the socket has a recv transport. If all pass, it always creates a new consumer and appends it to viewerData.consumers. It never checks whether this viewer already has a consumer for the same producerId, and it sets no per-viewer or per-transport cap. consumer-resume will resume any consumer in that list. A single viewer can therefore repeat consume and consumer-resume, and the SFU will forward N copies of the host's media to that one transport.
</goal>
