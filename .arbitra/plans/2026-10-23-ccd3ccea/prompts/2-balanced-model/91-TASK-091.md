# TASK-091 · Time-bound and session-own the fallback-consume-start acknowledgement without breaking the server's { ok } ack contract

Suggested model: a balanced model (such as Claude Sonnet), effort high. Why: Concurrency: ack lifetime versus reconnect and leave, and ordering of a socket-wide stop against a newer start on the same connection; Cross-file coupling: the server's { ok } ack contract differs from socketRequest's { success } contract; Scope: one callback, a small new helper module, and resets in a few handlers; Dependency: builds on the TASK-090 session generation and the TASK-087 subscription ledger; Blast radius: medium. Affects OBS relay-first viewers

You are a careful senior engineer making one change in this repository. Read the material below before you edit anything, keep to the constraints, and stop and ask if something does not match what this prompt says.

<goal>
Prevent a lost fallback-consume-start ack from latching isEnteringFallbackRef, and prevent a late ack from tearing down newer sessions or starting a player for a departed room. Successful fallback starts must keep working with the server's { ok: true, fallbackAvailable } acknowledgement. Compensation for a stale or timed-out ack must never remove a newer fallback subscription.

This matters because it fixes:
- fallback-consume-start uses an un-timed ack; a lost ack latches isEnteringFallbackRef and blocks fallback, and a late ack starts a player regardless of state (medium)
  Other requests in this file go through socketRequest with timeouts. enterFallbackMode instead uses a raw socket.emit with an ack callback and no timeout. isEnteringFallbackRef is set to true before the emit and is cleared only inside the ack or in exitFallbackMode. If the connection drops after the emit, socket.io-client never invokes that ack. onReconnect then resets fallbackMode to false but not isEnteringFallbackRef. Its call to enterFallbackMode() returns immediately, and so does the auto-enter effect. The viewer can no longer enter fMP4 fallback. If the server never answers, the UI stays in 'connecting' indefinitely, because the 40s watch safety timeout does not cover this path. The ack callback also never checks whether the viewer is still joined, whether the room ended, or whether another session has started. A late ack therefore calls cleanupPlayback(), which can tear down a session started meanwhile. It also creates and starts an fMP4 player, falling back to codeInput when joinedRoomCodeRef has been cleared.
</goal>

<steps>
1. Add src/lib/timedAck.mjs exporting emitWithTimedAck(socket, event, payload, { timeoutMs }). If !socket.connected, reject immediately with a not-connected error and do not emit, so the start cannot be buffered into a later connection. Otherwise emit once with an ack and resolve with the raw response, without inspecting success or ok. Reject with a distinguishable timeout error after timeoutMs, and with a disconnect error on the socket's 'disconnect' event. 2. Do not use socketRequest for fallback-consume-start, because its { success } contract rejects the server's { ok: true } acknowledgement.
3. At entry, capture the session generation and a fallback token. Call ledger.claim('fallback', token, socket.id) in the same synchronous block as the emit.
4. After resolve: if the session is stale, the viewer is not joined, or terminalRoomEndedRef is set, compensate and return without calling cleanupPlayback or creating a player. To compensate, emit fallback-consume-stop only if ledger.canRelease('fallback', claim, socket), then call ledger.release. Otherwise, classify the raw response exactly as the current callback does, and keep its success and failure branches.
5. On timeout: compensate the same way. The server may still process the start, and a stop on the same connection is ordered after it. Then reset fallbackMode and fallbackState, set an error, and latch fallbackStartRejectedRef. Joining or host-reconnected clears the latch, as today.
6. On a disconnect or not-connected rejection, emit no stop: the subscription belonged to the old socket.id. Reset the UI as for a timeout but do not latch the rejection, so onReconnect can retry.
7. Route the fallback-consume-stop in exitFallbackMode through the ledger: emit only when canRelease is true for the current claim, then release.
8. Clear isEnteringFallbackRef in a finally block, and also in onReconnect, handleLeave and onRoomEnded.
