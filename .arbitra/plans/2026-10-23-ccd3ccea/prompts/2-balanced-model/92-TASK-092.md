<context>
- The current ticket name embeds Date.now() before the async mkdir and writeFile, and acquirers then wait until tickets[0] === ticketName. A late publisher with an earlier key can also observe itself first and enter, while the existing holder never rechecks (C-5483ef840d06).
- Critique PC-092-LIVE-LOCK-RECLAMATION: age alone cannot prove abandonment. A live test running longer than any staleMs would lose its lock while still using the shared server. Rename-then-remove reclamation can also move a replacement owner's lock when two reclaimers act on the same stale observation.
- Safety argument for the revised design. The lock file for token T can be removed only by T's owner through release (owner alive, token matches) or by the single winner of reclaim-<T> (T's owner is dead, so it cannot release). A winner re-reads the lock while holding the marker and unlinks only if the token is still T, so it can never remove another token's lock. A late reclaimer either gets EEXIST on the marker or wins a fresh marker after the earlier winner finished, re-reads, sees a different token, and aborts.
- PID reuse or an unknown owner errs toward 'alive', which can stall acquisition but never admit a second holder. The bounded acquire timeout turns a stall into a clear failure.
- Ordered by arbitra, not a functional dependency: waits for TASK-088 because both edit tests/browser/media-flow.spec.mjs, so their changes land one after the other.
</context>

<steps>
1. Acquire: create the lock directory (recursive mkdir is fine for the directory only). Write metadata JSON { pid: process.pid, hostname: os.hostname(), workerIndex, token: crypto.randomUUID(), acquiredAt } to a unique temp file in the same directory. Then call fs.link(tempPath, lockPath). On success, unlink the temp file and return. On EEXIST, read the holder record and decide whether to wait or reclaim. Always unlink the temp file on exit paths.
2. Liveness: treat the owner as dead only if record.hostname === os.hostname() and process.kill(record.pid, 0) throws with code ESRCH. Treat success, EPERM, any other error, a different hostname, or an unreadable or unparseable record as alive or unknown, and keep waiting. Do not use lock age, mtime or any staleMs for reclamation.
3. Reclaim when the owner is dead: try fs.link(ownTempOrMarkerSource, path.join(dir, `reclaim-${record.token}`)). On EEXIST, back off and retry acquisition later. On success, re-read lockPath. If it is missing or its token is not record.token, abort the reclaim without touching the lock. Otherwise unlink lockPath. In all cases delete the reclaim marker only after that step completes, then retry acquisition. Never use rename on lockPath.
4. If a reclaim marker exists for the current holder's token and that marker's own reclaimer pid is dead, do not reclaim further. Keep waiting until timeoutMs, then fail with a diagnostic naming the lock record, the marker and the manual cleanup step (delete test-results/.media-flow-lock).
5. Release: read lockPath, and unlink it only if the record token equals the caller's token. If the token differs or the file is missing, throw an error stating that exclusivity was violated, so the test run fails visibly.
