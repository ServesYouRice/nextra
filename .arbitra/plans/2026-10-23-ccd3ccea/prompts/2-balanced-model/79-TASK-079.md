# TASK-079 · Sequence rollback safely: verified stream stop gates every later inverse, and a settle delay before restart

Suggested model: a balanced model (such as Claude Sonnet), effort high. Why: Concurrency/timing: ordering and wait correctness against an external process (OBS) whose acknowledgements precede the real state change; Failure-mode severity: a wrong order can crash OBS in obs.dll or restart a stream on a half-reset pipeline; Coupling: interacts with TASK-078 journal semantics and the TASK-080 deadline budget; Verification difficulty: needs deterministic fake-timer and request-order tests rather than live OBS

You are a careful senior engineer making one change in this repository. Read the material below before you edit anything, keep to the constraints, and stop and ask if something does not match what this prompt says.

<goal>
Make rollback treat a StopStream inverse as a gate. Poll until the stream is inactive, and if stopping fails or cannot be verified within a bound, dispatch no further inverse. Wait the video-settle delay after the last video-affecting restore before dispatching a StartStream inverse.

This matters because it fixes:
- Rollback restores configuration without waiting for stream shutdown (high)
  <quotes> src/lib/obsWebSocket.js:492-493 } else if (requestType === 'StartStream') { rollbackSteps.push({ requestType: 'StopStream' }); src/lib/obsWebSocket.js:502-504 for (const step of rollbackSteps.reverse()) { try { const response = await sendRequest(step.requestType, step.requestData); src/lib/obsWebSocket.js:233-234 await delay(250); const nextStatus = await getStreamStatus(sendRequest); </quotes> Rollback treats a successful StopStream response as completed shutdown and immediately dispatches the next inverse configuration mutation. Unlike the forward stop path, it never polls for inactivity. When OBS acknowledges stopping before the output actually finishes, restoring video, service or encoder-related settings races the still-active replacement stream.
- Rollback restarts the stream right after restoring video settings, skipping the settle delay the forward path uses to avoid an OBS crash (medium)
  The StopStream sent by stopActiveStream is the first mutation recorded, with StartStream as its inverse. SetVideoSettings is recorded later. Rollback replays the inverses in reverse, one after another with no pause. So it restores the previous video settings, which resets OBS's video pipeline, then restores the stream service, then immediately issues StartStream. The forward path waits 1200 ms before StartStream for exactly this reason. Its comment says that starting the encoder while a video reset is in flight can crash OBS in video_output_connect2.
</goal>
