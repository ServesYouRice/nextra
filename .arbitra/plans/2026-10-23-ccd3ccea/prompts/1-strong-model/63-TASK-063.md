<goal>
Every asynchronous step of start sharing checks that its operation is still current. A stale operation always releases the resources it acquired itself. Destructive compensation against shared singletons (the socket-scoped host-stopped and the OBS output stop) runs only when no successor operation exists. Server-facing room operations are serialized so that such compensation always precedes a successor's room request. No state or OBS channel is created for a torn-down session.

This matters because it fixes:
- Pending sharing operations can continue after teardown (high)

While the capture chooser is pending, isSharing is false and the navigation guard is absent. Component teardown can therefore finish before capture resolves; the continuation then installs the newly acquired stream and proceeds toward publishing without another mounted-session check. Similarly, the UI enables stopping before OBS configuration finishes, but the configuration continuation can still update state and open a control channel after stop or terminal cleanup.
</goal>
