TASK-045 (lane package): downloadFileWithRedirects in scripts/package-app.js now rejects in bounded time on a stalled server, a reset or early-closed connection, an aborted response and a file-stream error, deletes the partial file first, and settles exactly once. Lint, typecheck and npm test (748 tests, 728 before plus 20 new) pass; tests/packageApp.test.js was also run six times in parallel with no failure.

Choices the prompt left open or where I differed:
- Signature: downloadFileWithRedirects(url, destinationPath, redirectsLeft = 6, options = {}); options is the new fourth parameter ({ connectTimeoutMs = 30000, idleTimeoutMs = 60000, get }), so the three callers (bundleCloudflared twice, bundleFfmpeg) are unchanged and use the defaults. The function is now exported.
- Timers: step 3 names request 'timeout' / request.setTimeout. I used explicit timers instead: a connect timer from the start of each request until the response headers arrive, and an idle timer that restarts on each 'data' chunk and each file 'drain' (a slow disk pauses the response, so its drains count as progress). Reason: they behave the same with an injected transport that has no setTimeout, and they bound the whole header wait, not only socket inactivity.
- Redirects now run inside one promise with one settle-once path (a hop counter marks a replaced request as stale) instead of recursing; the redirect response and its request are destroyed rather than drained. The limit is unchanged (6 redirects, the 7th fails with "Too many redirects").
- HTTPS-only: the default transport is a small wrapper that refuses any non-https URL (also one reached through a redirect) before connecting; a test checks that a plain-http server receives no request. An injected `get` replaces it entirely, which is how the tests reach a local http server.
- Failure cleanup waits for the file stream's 'close' before deleting the destination (an open handle cannot be deleted reliably on Windows, and a not-yet-opened stream would create the file after the delete), then rejects. Nothing is deleted if no file stream was ever created, and a directory at the destination is never removed (rmSync without recursive refuses it).
- Two defects beyond the prompt's list were in the same callback and are fixed with it: fs.mkdirSync/createWriteStream throwing and an unparsable Location header both threw inside the response callback (an uncaught exception, not a rejection); both now reject.
- Scope: the real downloads (GitHub cloudflared, FFmpeg builds) were not run, because the prompt does not require `npm run package`. The default transport was checked once ad hoc against a local TLS server (repo certs, NODE_EXTRA_CA_CERTS): 200, empty 200, 301 to 200, redirect to http refused in 1 ms, silent server rejected after 400 ms.
