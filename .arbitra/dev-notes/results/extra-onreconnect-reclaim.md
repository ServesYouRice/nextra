extra-onreconnect-reclaim (socket lane, branch lane/socket; 617ac23 plus `git merge dev` = a03549d, dev at 797c195; found while carrying out run-ccd3ccea's plan, not a plan item): the gap extra-reclaim-pause-flake left open in HostView's onReconnect is real, and is fixed in commit 0034948 on lane/socket.

Cause (confirmed from the code and by a browser test): after a sharing host's socket reconnects, onReconnect (the 'connect' handler effect) sent `socketRequest(socket, 'reclaim-host', { code, hostToken })` with no signal and socketRequest's default two attempts for reclaim-host. When the first attempt is cut off after the emit ('disconnect-after-emit', retried because reclaim-host is idempotent), the second waits in waitForSocketConnect. If the host then presses Stop Sharing or confirms leaving the host view, the teardown's host-stopped is buffered (socket down) and the effect's cleanup only removed the 'connect' listener. On reconnect Socket.IO flushes the buffer first (onconnect: emitBuffered, then 'connect'), so host-stopped reaches the server from a socket that does not host the room (findRoomByHost misses: a no-op), and the waiting attempt then sends reclaim-host: reclaimHostRoom hands the room to that socket, clearHostReconnectTimer runs, viewers get host-reconnected, and nobody streams. The stale handler then went on to send request-server-config and get-room-metrics (and would have called terminateHostSession on a stopped view if the answer had been terminal). Server log of the unchanged client in the test (socket-extra-onreconnect-before-diag.txt): "Host transport ... closed during recoverable reload window for room XT86PZ" (the page left), then "Host LhRL5VQpQHBWoQRcAAAC reclaimed room XT86PZ" from the held reconnection; page events there: host-stopped, reclaim-host, request-server-config, get-room-metrics.

Paths in HostView that send a host-claiming request (the server has two: reclaim-host and create-room; there is no resume or rejoin event, and join-room is the viewer's), and whether one could still go out after the host leaves, stops sharing or unmounts:
- onReconnect's reclaim-host, attempt waiting for the socket (the second, after a cut-off first): OPEN, the defect; fixed.
- onReconnect's reclaim-host, attempt already emitted and waiting for its ack when the host stops: sent before the host-stopped on the same socket, so the server handles reclaim then stop (no takeover); its follow-ups (request-server-config, get-room-metrics, setRoomMetrics, or terminateHostSession on a terminal answer) still ran for a stopped session. Now the ack wait ends at once and nothing follows.
- onReconnect for a 'connect' after a teardown whose React commit has not run yet (a teardown from a non-React event, e.g. the capture's 'ended'): the stale closure still sees isSharing, but cleanup() nulls hostTokenRef synchronously, so it returned early (closed before). A second attempt already waiting in that case was open the same way as above; cleanup() now aborts the signal in the same task as the host-stopped, without waiting for the effect cleanup.
- Mount reclaim of the stored room (reclaimWithRetry): closed by 617ac23 (its own AbortController, aborted by the effect cleanup); no Stop Sharing is possible before it has reclaimed. Not changed.
- Start Sharing's room step (leave-room, create-room in createStartAttempt.requestRoom): the start guard re-checks staleness before each request; a create-room already waiting for the socket is still sent on reconnect, but it makes a new room no viewer is in, and abandonIfStale ends it with host-stopped once the answer arrives (mayCompensateShared). Closed by the guard; not changed.
- Resume Sharing: sends no claiming request (requestRoom({}) with no create; the mount reclaim took the room); its media requests are not claims and a stale one is dropped by abandonIfStale. Not changed.

Fix:
- src/lib/hostRecovery.mjs: new reclaimAfterReconnect({ request, code, hostToken, signal }), the onReconnect reclaim request, which hands the optional signal to socketRequest (options unchanged without one). To give the unit test a seam, the request was first moved here unchanged (no signal) and the test run against that (the failing output below), then the signal was added.
- src/HostView.jsx (onReconnect effect and cleanup() only): one AbortController per effect run, kept in reconnectReclaimRef; its signal goes to the reclaim and to the get-room-metrics after it; the effect's cleanup aborts it (Stop Sharing and every teardown change isSharing/roomCode; leaving the view unmounts), and cleanup() aborts it too, in the same task as the teardown's host-stopped. A 'cancelled' rejection returns silently. The effect re-runs only on socket, isSharing, roomCode or terminateHostSession, which are stable while one room is shared, so a reclaim for a live session is never aborted. OBS queue (TASK-071) and relay recorder (TASK-072) code untouched.
