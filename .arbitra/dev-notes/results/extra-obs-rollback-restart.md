extra-obs-rollback-restart (lane obs, commit c130355 on lane/obs, from dev 7747a2d): not a plan item; the defect TASK-102's todo test found. A failed setup no longer starts again a stream that OBS was only retrying when the setup began. Fixed; the test failed on the unchanged code.

Defect: configureObsStream's stopActiveStream sent its StopStream through the transaction, so a StartStream was journaled for it. A setup that failed later restored the previous service, then sent that StartStream: OBS went back to retrying the dead room (and re-created the stale encoder the reset exists to clear), while the result said "OBS settings were restored".

Behaviour chosen, per case:
- Healthy live stream (outputActive true, outputReconnecting false): the stop stays journaled, so the rollback restores the previous service and starts the stream again after the video settle time. That stream was the host's output and its target answered. This is what earlier items built and pinned: TASK-079's stop gate and settle wait before a StartStream inverse, the transaction tests (journalStreamReplacement ends the rollback with StartStream), and 'a setup whose stream cannot be confirmed stopped...' which expects 'skipped StartStream' for a live stream. Q-2 left this case unpinned; it is now pinned.
- Stream only retrying (outputReconnecting true): stopped over the housekeeping channel (not journaled; refused after the deadline like other housekeeping), so it stays stopped.
- State unknown: (a) OBS says the output is up but does not report outputReconnecting: treated as not live. It is stopped unjournaled and stays stopped, and the encoder-reset test stream now runs for it (the reset's own rule: unless a stream known to be running was stopped, a stale encoder must be assumed). (b) GetStreamStatus unreadable at setup start: as before, taken as no stream. Nothing is stopped by the setup and nothing is journaled; the reset's test stream is stopped as always, and the rollback starts nothing. Why this is the safe side: a start puts whatever OBS is compositing on the wire to whatever target the restored service names. If that target is gone, OBS retries it and sets its encoder up again. A stream left stopped is visible and takes one click in OBS to start, and the result says so.
- Result message: when the rollback had no failures and the setup stopped a stream that was confirmed down, the message now names what became of it. Live: "The stream OBS was running when the setup began was started again." Retrying: "OBS was retrying a stream whose target did not answer when the setup began; that stream was left stopped." Partial status: "OBS did not report whether the stream it had when the setup began was live, so that stream was left stopped." The clause follows "OBS settings were restored." (timeouts and AV1) and comes before the AV1 hint. It is added to the other failure messages too, which make no restore claim. Nothing is added when the rollback is incomplete (its failures are listed instead), or when the stop could not be confirmed (that message already says OBS is still streaming).

Change (src/lib/obsWebSocket.js): stopActiveStream(sendRequest, stopUnjournaled). wasLive is now `outputActive === true && outputReconnecting === false` (before: `outputReconnecting !== true`), and the stop goes `(wasLive ? sendRequest : stopUnjournaled)`. The call site passes housekeepingRequest, not the raw sender TASK-102's prototype used, so the unjournaled stop is refused once the deadline has passed. It returns `retrying` as well. configureObsStream keeps the stop result once the stream is confirmed down, and finish adds the clause above.
