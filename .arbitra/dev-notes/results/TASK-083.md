The transaction has a new registerUndo(label, undo) for steps that are no OBS request; configureObsStream registers an undo for a write the server applied. Verify command (`node --test tests/obsWebSocket.test.js tests/obsWebSocketWire.test.js`: 68 pass), lint, typecheck and npm test (1218 tests, 0 fail) pass.

Notes:
- The server cannot restore the file yet. `writeStreamEncoderSettings` (lib/obsProfile.js) merges into the file and returns only { ok, path }; the `obs-encoder-settings` handler in lib/socket.js answers { success, applied, reason }. Both are out of scope by the prompt ("Do not change lib/obsProfile.js, the server side of the restore endpoint"), and there is no restore endpoint in the repository. So the client side takes the contract the prompt describes: an answer may carry `previous`, and the undo passes it to writeEncoderSettings again. Against today's server there is no `previous`, so every failure after a successful write (a refused auto-start, "streaming stopped immediately", a request that timed out, the deadline) now ends 'Rollback incomplete: encoder settings file: not restored (its previous contents are not known)' and no longer says 'OBS settings were restored' (AV1 and timeout cases) where the file was in fact left changed. To make it a real restore, a later item must have writeStreamEncoderSettings return what the file held before (or the keys it had) and the handler pass that on as `previous`; the merge semantics matter there: a key the file did not have before cannot be removed by writing `previous` back through a merge, so the server must decide what `previous` has to contain.
- Beyond the prompt: (1) a note is registered before the write and released when the answer arrives, so a rollback that begins while the write is under way (the deadline; the write has its own 5 s timeout in HostView) fails with 'not restored (a write of it was still under way, ...)' instead of claiming a restore. The late write is not undone. (2) The registered undo also runs when the stop gate ended the rollback for the OBS requests (the gate protects OBS from changes under a live output, a file is not one); the OBS requests are still listed as skipped. (3) hold() and registerUndo() share one journal function; hold is unchanged.
- A write that threw (timeout, connection lost after the emit, a server refusal) is treated as not applied, as before, and registers nothing. A timeout after the server already wrote the file would still leave the file changed with the message claiming a restore; the injected function cannot tell that apart from a refusal (socketRequest tags the phase on the error, but obsWebSocket.js is socket-agnostic). Left as is.
- The hard cap (deadlineGraceMs, 18.7 s) was not widened for the file restore: it is bounded by writeEncoderSettings' own timeout (5 s in HostView), and a restore that does not finish in time ends 'Rollback incomplete: not finished ...', which is accurate.

The deadline test uses an OBS that is live at the start, so the setup goes straight to the write and the 300 ms deadline cannot fall into the encoder-reset test stream.
