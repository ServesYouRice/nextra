TASK-080 (lane obs, branch lane/obs): the transaction deadline now goes through configureObsStream's finish, so the rollback runs over the open connection before the socket closes. withObsConnection hands its callback { signal, onDeadline }; a callback that registered a handler gets the signal aborted and the handler called with the timeout result, and a hard cap (deadlineGraceMs) settles the transaction if the handler does not. Notes:
- Budget: the hard cap is 18.7 s after the 30 s deadline (OBS_WS_DEADLINE_GRACE = 10 x 250 ms stop gate + 1.2 s video settle + 3 x 5 s request timeouts), so a setup that times out settles within 48.7 s at the very worst; normally the rollback takes milliseconds. The TASK-079 worst case of a hung OBS (every status poll timing out at 5 s each) is deliberately cut off by the cap: the result then ends 'Rollback incomplete: not finished 18700ms later, so the connection was closed.'
- The result message after a timeout with a clean rollback is 'OBS setup timed out after 30000ms. OBS settings were restored.' (plus 'Disable AV1 mode and retry to use H.264.' in AV1 mode, as before); with failures it is '... Rollback incomplete: <failures>'.
- Beyond the prompt: (1) the transaction now journals mutations that are sent and still unanswered, because the setup is stuck inside exactly such a request when the deadline hits and its inverse would otherwise be journaled only after the request fails, i.e. after the socket closes; a StopStream is excluded, as for a timed-out one (TASK-079). (2) A mutation whose snapshot read ends after the rollback began is refused instead of sent. (3) configureObsStream has a new optional connectionOptions seam (timeouts, socket class), like transactionOptions. (4) A failure or rollback already under way when the deadline passes is not restarted or cut off at the deadline; only the hard cap bounds it, so its own message is kept.
- The prompt says to "abort in-flight work": the deadline does not reject the stalled request (it stays pending until its own timeout or until the connection settles, which rejects it and lands in finish's no-op guard); what stops is new work: the transaction refuses requests once its rollback has begun, and the housekeeping test stream (releaseStaleEncoder, sent raw) is refused once the signal is aborted.
- Not fixed, outside this item: releaseStaleEncoder's StartStream is sent raw and is not journaled, so a deadline (or any failure) that interrupts the short test stream between its StartStream and StopStream leaves that stream running; the rollback does not stop it. This predates the item (a thrown request error does the same).
- The tests use real timers with short timeouts, not fake timers (the repository's existing OBS tests do the same). The slowest of the new ones takes about 1 s (a rollback that outlasts the deadline).
