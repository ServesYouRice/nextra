It lets the broken MediaSource go at once (cleanupMediaSource, generation -1) and rebuilds through `resetAndRequestInit` (TASK-065's bounded init request). `failureRecoveries` counts rebuilds until media (not just the init segment) goes into a rebuilt SourceBuffer, capped at `MAX_INIT_TIMEOUT_RETRIES` (Q-008: constants reused). The fourth failure in a row is the one terminal error. The 'sourceclose' and video 'error' listeners are added per MediaSource and removed on every rebuild and in stop(). QuotaExceededError handling, the append/ack flow and the overflow path are unchanged.
- Where this differs from the prompt's wording:
  - onError fires once per episode, when the player gives up. It does not fire when the failure first happens. The SourceBuffer 'error' path already recovered without calling onError, and the VAL-092/VAL-093 tests pin that (`errors` stays [] while it recovers). In browsers, a parse error fires that event and the video 'error' for the same failure. Reporting from one trigger and not the other would make the report depend on which event comes first. So every trigger stays silent while it recovers (a console.warn per rebuild), and the one onError comes with the 'error' state. VAL-094 says "at most one onError/console.error per failure episode", and this keeps to it. Its evidence line "onError is called once" for the 11-fragment case is met as zero while recovering.
  - The "failure latch" is not a separate flag. Every failure tears the broken MediaSource down at once and sets the generation to -1. So the failed SourceBuffer is never current again, and handleMediaChunk drops the failed generation's fragments at its generation check. The episode counter is the latch the prompt describes in step 1: it is cleared only by a successful media append on a new SourceBuffer.
  - The "teardown flag" of step 4 is also not a separate boolean. The handlers check that the player is not stopped and that the MediaSource is still the player's. cleanupMediaSource removes the listeners before it tears anything down, and stop() and rebuilds only change the element's src after that, so a close the player causes cannot reach a live handler. The tests show it for stop() and for a rebuild.
  - Step 3 was already true: resetAndRequestInit nulls sourceBuffer and mediaSource before it asks again. The exception path just never reached it. A test shows that the same generation is now accepted after the reset.
- Log change: the SourceBuffer 'error' path now logs console.warn (with the attempt count), not console.error.
- Left open, for the owner:
  - A failure that the decoder reports only after media went in successfully starts a new episode each time. A stream whose appends succeed but which the decoder always rejects would be rebuilt again and again: one warning and one init round trip per failure, never onError. Catching that needs a playback-progress signal; the prompt defines success as a successful append.
  - After the terminal error, an init the server pushes still rebuilds the player, as after any other terminal error of this player. If that rebuild fails before media goes in, it is final at once.
