TASK-020 (lane whip, commit 6078ef8 on lane/whip): parseOffer now records every m-section in offer order (index, kind, port, proto, formats, mid) in `parsedOffer.sections`. `parsedOffer.video` and `.audio` are kept, and are the first section of each kind with a supported codec. createAnswer answers each offered section in offer order: accepted sections exactly as before, every other section as `m=<kind> 0 <offered proto> <first offered fmt>`, `c=IN IP4 0.0.0.0`, the offered a=mid and a=inactive. a=group:BUNDLE lists the accepted mids only, in offer order. Only lib/whip.js and tests/whip.test.js changed. Four new tests failed before the fix; the video-first regression guard passed before and after. Full npm test: 505/505; lint and typecheck pass.

Prompt corrections:
- Step 4 said to "keep" accepting the first supported section of each kind. The old parser actually kept the last section of each kind (each new m=video replaced parsedOffer.video). It now takes the first section with a supported codec and rejects the others with port 0.
- The prompt did not mention a parser defect that the fix depends on: the old parser only recognised m=video and m=audio lines, so the a=mid of an m=application section (and its other attributes) were applied to the audio or video section before it. A data channel offered after video renamed the video's mid. Attributes of other kinds now stay with their own section.
- The rejected-section line list in step 2 leaves out c=. It is included, because the answer has no session-level c= line and SDP requires one in each media section in that case.
- When no section is accepted, the a=group:BUNDLE line is now left out instead of being emitted empty (RFC 8843 §7.3.1). The WHIP route never reaches this, because it returns 409 without supported video.
- RFC 8843 §7.3.1 lets the next accepted mid become the tagged section when the first offered one is rejected; the answer does this (the first mid in the answer's BUNDLE is the first accepted one).

Left open: an offered section with port 0 (disabled, or bundle-only) is still treated like any other section. Hand-built parsedOffer objects without `sections` still get the old video-then-audio answer of their accepted sections.
