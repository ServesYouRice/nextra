What changed
- consumeProducer starts playVideoElement without awaiting it, as the relay path does (steps 1). No await on playVideoElement remains in WatchView. The autoplay-denial muted retry runs inside playVideoElement, so the existing autoplay test still passes.
- waitForTransportConnected (playbackAttempt.mjs) replaces the inline ICE promise: same 2 s/8 s values and the same three messages. It also rejects at once when the transport is closed (mediasoup-client's close() emits no connectionstatechange but does emit transport.observer 'close'), which resolves the note in TASK-087.md: a superseded mediasoup attempt no longer waits out its ICE timer when cleanupPlayback closed its transport. A transport already in 'failed' or 'closed' when the wait starts now rejects immediately with 'WebRTC connection failed./closed.' (before, it waited for the timer, because the old code only listened for later events).
- withDeadline(attemptRef, start, { ms = 40000, message }) (step 3): begins the attempt and hands it to `start`, so startMediasoupPlayback takes a new optional `attempt` argument (default: begins its own, as handleWatch's call does). At expiry a still-current attempt is superseded (new attempt.supersede()), its own resources are disposed, and the result rejects with PlaybackDeadlineError (default message 'Connection timed out. Check your network or try again.', handleWatch's). An attempt a newer owner replaced rejects with SupersededAttemptError and the newer attempt is left alone. Wrapped: handleTryMediasoup, recoverTransport's WebRTC start, rejoinAfterReconnect's WebRTC start. The existing catch blocks report the PlaybackDeadlineError like any failure (handleTryMediasoup shows the message, cleans up and clears loading in its finally; the recoveries fall back to the relay when relay is allowed).

Where the prompt was off, and choices made
- Step 4 suggests a tunnel-host origin without TURN. On a tunnel origin Watch goes relay-first, which works against the test host, so WebRTC is never tried; the tests use a direct origin with relay-only ICE instead (ICE blocked by an RTCPeerConnection subclass that forces iceTransportPolicy 'relay'; the test server offers no TURN server). The tunnel fail-fast message and its 2 s value are unchanged and not covered by a new browser test.
- Try WebRTC exists only in OBS fallback mode, which the test server cannot reach (WHIP is off), so handleTryMediasoup's deadline has no browser test; the 40 s deadline is tested with short timers in tests/playbackAttempt.test.js. The reconnect-recovery test covers the recovery path end to end.
- The prompt says the ICE timeout is installed after the consume loop; that stays (it has to start after the first consume, which is what starts ICE). The window now starts right after the consume loop instead of after play() resolves, so a connection that needed more than 8 s after the first consume used to have been tolerated while play() waited, and now falls back to the relay. The 8 s value is the one the prompt asks to keep.
- The deadline wraps only the WebRTC starts. The relay fallback that follows a failed recovery start keeps its own timers (7 s media-init, 5 s sourceopen, 18 s first buffer, 15 s acks), so a recovery's total is not capped at 40 s; only handleWatch has an overall cap across both modes.
- The prompt's verify commands say 'ask before running'; per the instructions they were run. Browser runs used run-e2e.cjs on the lane's own ports (the driver retired the lock mid-task; a lock wait I had queued was stopped before it ever held the lock).

For the owner
