TASK-024 (lane whep, commit 10f759e on lane/whep): the WHEP viewer capabilities and the answer now carry only header extensions and RTCP feedback the viewer offered, and an extension is answered only under the id the consumer stamps. Only lib/whep.js and tests/whep.test.js changed. Fifteen new tests failed before the fix. lint, typecheck and npm test (525 tests) pass.

- buildViewerRtpCapabilities: a router header extension is kept only when the receiving section (the first section of the kind that can receive, which is the one createViewerAnswer gives the consumer to) lists the same uri; its preferredId is the offered id, so mediasoup keeps the consumer extension only when that equals the router id. The consumer's codecs now get only the rtcp-fb the offer listed for the matched payload type or by `a=rtcp-fb:*`, and the codec objects are copies.
- buildActiveSection: extmap lines come from consumer.rtpParameters.headerExtensions, limited to the offered (uri, id) pairs, each id and uri once; rtcp-fb lines are the consumer codec's feedback that the offer listed for the answered payload type or by wildcard (a codec with no matching offer payload type gets the wildcard only). parseViewerOffer reads `a=rtcp-fb:*` (payloadType '*').
- Aligned buildViewerRtpCapabilities with isOfferSectionEligible, as TASK-023 left open: a sendonly section no longer counts as active, and codecs and extensions are no longer collected from disabled or inactive sections of an active kind. Codec selection and payload types are otherwise unchanged (the 'keeps the router codec and payload type selection' test passed before and after).

Existing assertions updated (both encoded the removed behaviour, nothing else in them changed):
- 'createViewerAnswer includes extmap from consumer headerExtensions': the second assertion required `a=extmap:4 ...transport-wide-cc-extensions-01`, but SAMPLE_OFFER lists no transport-cc extension for video. It now asserts the answer does not advertise one. The sdes:mid assertion is unchanged.
- 'createViewerAnswer includes rtcp-fb lines': SAMPLE_OFFER lists no rtcp-fb at all, so the nack, nack pli and transport-cc lines were advertised unoffered. The test now builds the offer from SAMPLE_OFFER with those three `a=rtcp-fb:96` lines added; its three assertions are unchanged. 'writes no rtcp-fb when the offer lists none' covers the old input.

Which extensions stay negotiated (verified with the real mediasoup ortc consumer logic, router from config.MEDIA_CODECS; router ids: mid 1, abs-send-time 4, transport-wide-cc 5, ssrc-audio-level 6, video-orientation 8, toffset 9, abs-capture-time 10, playout-delay 11):
- Chrome-like offer (video: toffset 14, abs-send-time 2, video-orientation 13, transport-wide-cc 3, playout-delay 5, mid 4; audio: ssrc-audio-level 1, abs-send-time 2, transport-wide-cc 3, mid 4): none. mid, abs-send-time and transport-wide-cc are all dropped, because mediasoup cannot renumber a consumer's extensions and RFC 8285 requires the answer to use the offered id. With no abs-send-time or transport-cc extension left, mediasoup also removes transport-cc and goog-remb from the consumer's feedback, so the viewer gets no sender-side bandwidth feedback; nack, nack pli and ccm fir stay (when offered). Before the fix the answer advertised them under the offer's ids while the RTP carried the router's, so the browser misread them (the router's transport-cc id 5 is playout-delay in Chrome's video numbering).
- An offer numbered like the router (mid 1, abs-send-time 4, transport-wide-cc 5, audio-level 6): all of those stay negotiated, with consistent ids. Whether a given WHEP client's numbering matches is client by client.
- If keeping transport-cc for Chrome matters, the router's ids would have to match the browser's, which needs a change in lib/mediasoup.js or mediasoup itself (both outside this item). Owner decision.

Prompt corrections:

- Step 2 says to emit extmap lines from the consumer's headerExtensions; the answer used to renumber them to the offer's ids, which is the defect, so the ids are no longer remapped, only filtered. Step 1's "set preferredId to the offer's id" is how a mismatched id is dropped.
- One thing the prompt does not mention: mediasoup matches a consumer extension by uri and id whatever the capability entry's kind, and the same capabilities object serves the video and the audio consumer. An entry built for one kind can therefore reach the other kind's consumer (the router uses the same id for the same uri in both kinds, e.g. abs-send-time 4). buildViewerRtpCapabilities leaves such an entry out when the other active kind's section did not offer that uri with that id. Cost: video offering abs-send-time at the router id 4 while audio does not offer it loses the extension for video as well. Valid bundled offers use one id per uri, and browsers offer mid, abs-send-time and transport-cc in both kinds, so this is rare. Passing per-kind capabilities from lib/whepRoutes.js would remove the cost; that file was not touched.
