extra-obs320-overflow (found while carrying out check 15; not a plan item): fixed on lane/libmisc in commit 9ce95fa. Lane at dev 437b8f2 (ff-merged from 8e68223 to get the per-lane Playwright ports).

Defect: on the host page at a 320px viewport with "Use OBS (WHIP ingest)" selected, the video section, the start button and the capture rows were 315.5px wide from a 16px inset, so the page was 12px wider than the viewport (documentElement.scrollWidth 332). With OBS off it was 320. README promises a 320px floor.

Cause (CSS only): the OBS tuning-profile toggle (`.mode-toggle` with Balanced / Crisp / Max, shown in `.controls` when OBS is selected) gives each button `min-width: 6.4rem`. Three cells plus the toggle's padding and border are 315.5px, but a 320px phone leaves 288px between the 1rem page paddings. Below 900px `.host-layout` is a column with `align-items: flex-start`, so `.host-video-section` is as wide as its widest content (min-content 315.5px). The stage (`width: min(100%, ...)`), `.controls` and `.capture-settings` take that width, and the section ends at x=331.5. The same happens without OBS once the host is sharing: the live "Resolution" toggle in `.controls` has three 6.4rem cells too (browser capture, probed: scrollWidth 332 at 320 and 330px). The page-level overflow starts below 330px; between 330 and 347px the section already sticks out of its 16px inset on the right without scrolling.

Fix (src/index.css, 13 lines with the comment): `@media (max-width: 21.7em) { .controls .mode-toggle button { min-width: 0; } }`, next to the `.mode-toggle` rules. 21.7em is 347.2px at the default font size: 3 x 6.4rem + 0.4rem padding + 2px border + 2 x 1rem page padding = 347.4px, so from 348px up the rule does not apply. em in a media query follows the browser's default font size, as the rem cell does. Below that the cells size to their labels (99.5 + 71.9 + 66.8px for Balanced, Crisp and Max at 320px), left-aligned in the full-width toggle box as the 6.4rem cells already are at 375px. src/HostView.jsx is untouched.

Proof it failed first (tests/browser/ui-semantics.spec.mjs, new loop "the host page reflows without horizontal scrolling at <w>px with OBS ingest selected" over the README widths 320..2560; output in the shared scratchpad, `libmisc-extra-obs320-before.txt`):
- 2 failed (chromium and mobile-chrome at 320px), 20 passed, 4 skipped: `host with OBS on at 320px (stage right edge 331.5, tuning toggle 331.5)`, expected <= 321, received 332.
- The bound is `documentElement.clientWidth` (layout viewport), not `window.innerWidth`: a first version using innerWidth passed on mobile-chrome at 320px on the unchanged code, because mobile Chrome widens innerWidth to fit overflowing content. The existing "content reflows without horizontal scrolling" test has that blind spot in the mobile project; it was left as it is.
After the fix: full ui-semantics spec 65 passed, 13 skipped (the existing desktop-only skips on mobile-chrome), 0 failed, one worker, on this lane's own ports (`run-e2e.cjs`). `npm run lint`, `npm run typecheck` pass; `npm test` 1380 pass, 0 fail.

Other widths unchanged: a probe compared the geometry of the host layout, section, stage, controls, toggles, capture rows and side panel before and after, in three states (idle browser capture, idle OBS, sharing with browser capture) at 320, 330, 340, 347, 348, 352, 353, 360, 375, 414, 480, 640, 768, 900, 1024, 1280 and 1440px (the sharing state at 480-768 was refused by the server's 10-rooms-per-minute limit, not a defect; 900-1440 were measured). Result: nothing moves from 348px up; only 320-347px change (and there only the overflowing layouts). Scratch files: `libmisc-extra-obs320-probe.cjs`, `-compare.cjs`, `-probe1.json` (before), `-probe2.json` (after) in the scratchpad.

Not fixed, for the owner (separate from this overflow, present before and after, also with OBS off): at 320-360px the capture rows' "Resolution" toggle (4K / 1440p / 1080p, cells at `.capture-settings .mode-toggle button { min-width: 5.25rem }`, in a grid of label + toggle) is wider than its row and is cut by the toggle's own `overflow: hidden`. At 320px the toggle is 214px wide for 258px of content, so about half of the 1080p cell is cut off, and the page does not scroll. Fixing it means stacking the label above the toggle or shrinking its cells at narrow widths; it needs its own test (assert `scrollWidth <= clientWidth` on each `.mode-toggle`).
