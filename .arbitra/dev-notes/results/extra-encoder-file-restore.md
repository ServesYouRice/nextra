Extra (not a plan item), lane netcheck, branch lane/netcheck, commit d1addd1 (on top of 13c4286): the encoder settings file is now really put back when a setup that wrote it fails. TASK-083 left this half done: the client journaled the write but the server never said what the file held, so every rollback ended "encoder settings file: not restored (its previous contents are not known)".

Result: after a refused auto-start or a request OBS never answers, with the file holding OBS-style CRLF JSON with extra keys, invalid JSON, or not existing at all, the rollback restores it byte for byte (or removes it) and the message says "OBS settings were restored" with no "Rollback incomplete".

Design (and one choice that differs from the prompt's example):
- `previous` is `{ restoreId, existed }`, not the old contents. The server keeps the file's bytes (or "no file") in memory (lib/obsProfile.js, `keptRestores`) and a restore names them by id. Reason: the host page sends the restore back as `settings`, so a restore that carried contents would let the page write any JSON into OBS's streamEncoder.json past `sanitizeEncoderSettings`' whitelist (it exists to stop arbitrary encoder options, e.g. x264opts/ffmpeg options, being passed through). With an id the page can only undo what the server itself wrote. The profile-name lookup (a name is only compared against profiles on disk) and the 5000-char/200-char name bound are unchanged, and a restore also needs the id to belong to the same profile's file.
- Restore mode replaces (writes the kept bytes through the same temp file + rename, or unlinks the file if the write created it); the write still merges. So keys the write added are gone after a restore, which a merge of old values could not do.
- Kept: at most 16 entries, 15 minutes, files up to 256 KB. A restore is spent once used (a second one answers `restore-unavailable` and touches nothing), so it cannot rewind the file over later changes by OBS or the user. A file that cannot be read (not "missing") or is over 256 KB is still written as before but `previous` is null, so the client honestly reports "not restored (its previous contents are not known)".
- Two writes in a row restore newest first back to the original (tested).
- No guard that the file is still what Nextra wrote before restoring: OBS may itself rewrite streamEncoder.json, and refusing then would bring the old failure back. A restore always puts back the bytes from before the write.
- Server memory only: a server restart between the write and the rollback loses the entry and the client reports `not restored (restore-unavailable)`. The rollback takes seconds and a restart drops the host's socket anyway.

Code:
- lib/obsProfile.js: `writeStreamEncoderSettings` returns `{ ok: true, path, previous }` (previous null when not restorable); new exported `restoreStreamEncoderSettings({ profileName, previous }, options)` returns `{ ok: true, path }` or `{ ok: false, reason }` with reasons `invalid-restore` (not a 32-hex id), `profile-not-found`, `restore-unavailable` (spent, expired, forgotten, other profile) and `write-failed`. `options.now` is a test seam for the age limit.
- lib/socket.js, `obs-encoder-settings` handler: same guards as before (the socket must host a room whose ingestMode is 'obs'; server.js still requires a loopback client). Settings that are a plain object with a string `restoreId` are a restore request: only the id is read and passed to the new `restoreObsEncoderSettings` option (default: `{ ok: false, reason: 'unavailable' }`); the answer is `{ success: true, applied, reason }`. A successful restore sets `room.obsEncoderSettingsApplied = false` (OBS no longer runs on the settings Nextra wrote, so relay viewers are not passed the source through); a refused one leaves the room as it was. A write answers with `previous` when the lib returned one; the answer never carries the path.
- server.js: `restoreObsEncoderSettings` wired with the same loopback-only rule and a log line.
- src/lib/obsWebSocket.js and src/HostView.jsx: unchanged. The client already sends `writeEncoderSettings({ profileName, settings: previous })`, which is exactly the restore request; its JSDoc ("`previous` ... passed to this function") stays true. No conflict with the obs lane's TASK-084.
- README.md: one sentence that a failed setup puts the file back.
