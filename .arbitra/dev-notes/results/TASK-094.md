How it behaves now:
- Tunnel mode means a loopback request addressed to the URL of the cloudflared tunnel Nextra launched (quick or named), while its status is 'active'. "Addressed to" uses the same Host / X-Forwarded-Host / Origin / Referer match as the known-share check. server.js provides `getManagedTunnelOrigin`. A SHARE_BASE_URL alone (status 'manual') is no longer a Cloudflare mode.
- `TRUST_CLOUDFLARE_CONNECTING_IP=true` (config.js, boolean, default false): CF-Connecting-IP from any loopback peer is the client. Only a single valid address counts. The flag works inside the existing forwarded-header gate (TRUST_X_FORWARDED_HEADERS, or a request addressed to a share URL). Outside that gate, the flag gives a per-viewer `public-share:<ip>` bucket. Nextra logs a line at startup when the flag is on. The flag is documented in README (an Internet Sharing bullet and a Public Sharing table row) and in .env.example. The README table also gained rows for TRUST_X_FORWARDED_HEADERS and TRUST_PROXY, which were not documented before and which the flag's row refers to.
- Without a mode, a loopback relay that forwarded headers do not cover now gets the one shared bucket 'public-share-proxy'. Before, it got 'public-share:<CF-Connecting-IP>', a bucket the client chose. The prompt's success criterion says no default path may read CF-Connecting-IP, and this path read it. A CF-only request under trusted forwarding is still 'unknown' (remote).
- getSocketIp and getRequestIp pass `resolveTrustedHopCount(config.TRUST_PROXY)` and the flag. They know nothing of the tunnel, so the flag is their only Cloudflare mode. getSocketIp's last line now uses the peer address it already worked out (the tidy-up check-20 suggested).
- lib/network.js gains `getCloudflareClientIp` (one valid address or ''), used by both paths, and a doc comment on parseForwardedFirst: it serves X-Forwarded-Proto and X-Forwarded-Host, and must never be used for the client address.
