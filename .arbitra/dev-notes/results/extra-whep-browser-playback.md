extra-whep-browser-playback (lane whep, commit 6849b18 on lane/whep, from dev cc37bf9). Not a plan item: found while carrying out run-ccd3ccea's plan (TASK-025 browser check). Result: fixed. WHEP playback now decodes video and audio in Chromium 153 and Firefox 155, for a VP8 + opus room and an H.264 + opus room. The new test failed on the unchanged code.

Design
- A WHEP player decodes only the payload types (PTs) of its own recvonly offer. A mediasoup consumer sends with its router's PTs: the worker stamps them as the producer's RTP enters the router, and the consumer never rewrites them (worker Consumer.cpp). So the only way to send other numbers is another router whose numbers are the offer's.
- lib/whep.js: planViewerPayloadTypes(offer, producers, routerCaps) finds, for each room producer, the router codec it is consumed as (from producer.consumableRtpParameters), the offer's PT for it (findOfferPt, so TASK-026's H.264 profile matching applies) and the offer's RTX PT. If the main router already has those numbers, nothing changes: the main router serves, as before. An offer numbered like the router still gets the same answer.
- Otherwise a "layout router" (lib/whepLayoutRouters.js, new) is used. It is a router on the same worker whose mediaCodecs pin the offer's PTs (preferredPayloadType). The room's producers are piped in with Router.pipeToRouter (keepId false, since both routers are on one worker; no SCTP; loopback UDP from 49152-65535, not the RTC range, which may be a single port). One router serves each room and numbering. Viewers whose keys it covers share it: every Chromium viewer, and a video-only viewer can use a video+audio router. Parallel requests share the one being created. It closes when its last viewer leaves (lease release in closeWhepSession) and when the room closes (closeAllWhepSessions). A replaced host producer is piped again on the next request; old pipes close with their producer. The cap is 4 per room and 16 per server (constants, also options); a request beyond it gets 503.
- RTX: mediasoup cannot pin an RTX PT. A video/rtx entry in mediaCodecs throws "UnsupportedError: media codec not supported". But it gives a video codec's RTX the next free number of its dynamic list (100-127, then 96-99) right after that codec. buildLayoutMediaCodecs therefore lists audio first, then pinned 'audio/SILK' filler entries on every unused number ahead of the offer's RTX PT, then the video codec. The RTX then lands on the offer's number: VP8 96/97 for Chromium, 120/124 for Firefox, H.264 108/109 and 126/127. Up to about 27 fillers; they are never offered by browsers or consumed. After the router is created its caps are checked. If the RTX did not land (a future mediasoup), the codec goes without RTX and a warning is logged.
- limitViewerRtxToOffer keeps an RTX capability only when the router's RTX PT is the offer's. mediasoup gives a consumer RTX if the caps hold any rtx codec, because it does not compare apt. When no RTX can match (the offer's RTX PT is outside 96-127, for example), the consumer has no RTX but keeps plain NACK. The worker then retransmits the original packet on the media SSRC (RtpStreamSend::ReceiveNack works without RTX). consume({ enableRtx: false }) would drop NACK too, so it is not used.
- An offer whose numbers no router can carry gets 400 with a clear message: one PT given to both video and audio, or a PT outside 0-127. TASK-024's extension handling, TASK-026's H.264 matching, check 17's DTLS setup role and TASK-025's truthful answer are untouched; the answer is still built from consumer.rtpParameters, which now equal the offer's numbers.
- Producers without consumableRtpParameters (the fakes in the existing route tests) cannot be planned, so the main router serves them as before.
- Files: lib/whep.js, lib/whepRoutes.js, lib/whepLayoutRouters.js (new), lib/mediasoup.js (createRouter(): only this module holds the worker, and the route needs a router on that worker; server.js and lib/socket.js are not changed), README.md (WHEP note), tests/whepPayloadTypes.test.js, tests/whepBrowserOffers.js (the recorded Chromium 153 and Firefox 155 offers, whole).

What mediasoup 3.27.1 can and cannot do (scratchpad whep-extra-playback-probe.txt)
- It can pin media PTs (preferredPayloadType), pipe between routers on one worker, give a consumer NACK without RTX, and keep simulcast through a pipe.
- It cannot pin an RTX PT (it can only be steered, as above), cannot renumber a consumer, and cannot set header extension ids per router (they are global, from supportedRtpCapabilities).

Left for the owner
- Cost per layout router: one more router, a loopback pipe transport pair (2 UDP ports on 127.0.0.1) and a second copy of all the room's media inside the worker, all simulcast layers. A room with both Chromium and Firefox viewers has two. The caps (4 per room, 16 per server) are constants, not env settings.
- The RTX steering relies on mediasoup's numbering order (3.27.1). The test 'layout router codecs steer mediasoup to the offer numbers' fails if an upgrade changes it; the server would then fall back to NACK without RTX and log it.
- Not exercised: retransmission. On loopback nackCount stayed 0, so neither RTX nor NACK-only recovery was seen working in a browser.
- Header extensions, same cause, not changed: mediasoup's ids are fixed per server (mid 1, abs-send-time 4, transport-cc 5), and Chromium (9/2/4) and Firefox (3/-/7) number them differently. Under TASK-024's rule, WHEP consumers therefore get no transport-cc or abs-send-time, so there is no bandwidth feedback for WHEP viewers. A layout router cannot fix this. Both WHEP and socket viewers showed 320x180 in this run, so no resolution effect is claimed.
- The TASK-025 unit tests in tests/whep.test.js ('with consumers built by the mediasoup ortc code') still describe main-router consumers for Chromium and Firefox offers. That stays true for createViewerAnswer, but the route no longer builds such consumers for those offers.
- Playwright on Windows cannot test Firefox WHEP against a 127.0.0.1 server (no loopback candidate). A WHEP e2e test would need a relay like the one here, or Linux.
