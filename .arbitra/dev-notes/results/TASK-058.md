TASK-058 (lane server): worker-crash recovery now follows the owner's answer 2 (option c). With `EXTERNAL_SUPERVISOR=true` the process tells rooms (MEDIA_WORKER_FATAL), cleans up, releases the port and exits 1 through the TASK-057 coordinator, spawning nothing. Without it, Nextra starts a visible replacement: an ordinary (not detached) child with stdio inherited, and the original process stays alive until it ends and exits with its exit code. Verify: `node --test tests/workerProcessRecovery.test.js tests/workerRecovery.test.js tests/shutdownCoordinator.test.js` (49 tests), lint, typecheck and `npm test` (1040 tests) pass.

How it behaves:
- New flag `EXTERNAL_SUPERVISOR` (config.js, boolean, default false), documented in README.md (Server table, Operational security bullet, Operations bullets with signal propagation per platform) and `.env.example`.
- `decideWorkerDeathAction` returns 'exit-for-supervisor' for a stable-uptime death when `supervised` is true; 'restart' keeps its name for the self-restart mode (the existing unit test pins it and stays unchanged); 'ignore' and the startup-crash 'exit' are unchanged.
- `launchReplacementProcess` (lib/workerRecovery.js) spawns with `stdio: 'inherit'`, no `detached`, no `windowsHide`; logs "[recovery] Started replacement Nextra (PID n)" at warn level (visible at LOG_LEVEL=warn); exit code of the replacement is the original's exit code (a signal death or an unknown code becomes 1); a spawn failure logs "[recovery] Failed to relaunch automatically" and ends with 1. On POSIX it passes SIGINT/SIGTERM/SIGHUP sent to the original alone on to the replacement; on Windows it passes nothing on (the console already delivers Ctrl+C, Ctrl+Break and a window close to both, and child.kill() there is TerminateProcess).
- lib/shutdownCoordinator.js gets a third phase 'restart' and `requestRestart(reason, { launchReplacement, notifyRooms })`: arms a 5 s force-exit timer (exit 1) first, tells rooms, waits the 150 ms flush, cleans up, closes the listener (waits at most 2 s for the callback, as the old code did), then launches. A stop signal during the restart is passed on to the replacement, or, before there is one, cancels the launch (exit 0). A fatal error during a restart stops the replacement and exits 1, so a supervisor restarting Nextra after that never meets a second instance. `requestFatal` takes an optional `notifyRooms` so the supervisor exit sends MEDIA_WORKER_FATAL instead of SERVER_FATAL.
- server.js: only the worker-death handler and the import on the workerRecovery line changed (the coordinator construction block is untouched, so TASK-103's server.js changes should merge without a hand fix). The `isShuttingDown` line from TASK-057 is kept as is.

Prompt notes and decisions:
- The prompt says "exit-for-supervisor versus self-restart"; I kept the existing action name 'restart' for self-restart instead of renaming it, because tests/workerRecovery.test.js asserts it and may not be edited.
- The prompt step 2 says "emit room-ended, cleanup, exit(1) through the TASK-057 exit funnel": done with `requestFatal('media-worker-died', { notifyRooms })`, which also arms the 5 s fatal force-exit timer.
- The prompt's "log the replacement PID" is done; "document signal propagation per platform" is in the README and in the comment on `launchReplacementProcess`.
- Timing change: readiness (`serviceReady`) now drops at once when the worker dies (onShutdownStart), where the old code dropped it 150 ms later in cleanup.
- scripts/smoke-packaged.js, lib/mediasoup.js, scripts/package-app.js were not touched. The packaged smoke was not run (the prompt does not require it); it only checks that the PID reported by /api/metrics changes and that /healthz stops after /api/test/shutdown, which still holds. Packaged note: the original (caxa-launched) node process now stays alive next to the replacement, so a packaged app shows two node processes after a worker crash (the old code left one detached process).
- Windows only: stopping the original with TerminateProcess (Task Manager, `taskkill` without /T) leaves the replacement running; the README says to use `taskkill /PID <pid> /T`.
- The before-fix run of the new integration tests left two detached replacement servers of the unchanged code running (the test's cleanup could not reach them while they were still starting); I stopped both through their /api/test/shutdown endpoints.
