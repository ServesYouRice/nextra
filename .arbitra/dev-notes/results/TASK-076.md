TASK-076 (C-009d5a411943): fixed on lane/fmp4.

- src/lib/fmp4RelayPlayer.js: `awaitingKeyframe` is set when the append queue is full (the dropped fragment takes the rest of its GOP with it). While it is set, `handleMediaChunk` queues only a fragment with `keyframeStart === true` and room in the queue; anything else is discarded. A keyframe fragment that is itself dropped for a full queue does not end the wait. The drop bookkeeping moved into `dropFragment`: fragments discarded while waiting count toward MAX_CONSECUTIVE_DROPS like full-queue drops, so a stall still ends in `resetAndRequestInit` at the 15th consecutive drop; `consecutiveDrops` starts over when a fragment is queued. The warning text is "Queue full, dropping fragment ..." as before, or "Waiting for a keyframe, dropping fragment ..." for the new case.
- `relay-ack` is emitted right after the fragment is queued (before processQueue), not at receipt. Dropped fragments, fragments discarded while waiting, duplicates (lastSequence) and empty chunks are not acked. The server's acks are cumulative (`recordFallbackAck` drops every unacked entry up to the acked sequence), so a gap simply leaves the oldest unacked entry older, which is what it should show: the viewer is behind.
- `lastSequence` is still updated for every fragment seen, before the checks, so the dedupe is unchanged. Generation handling is unchanged.
- Decisions the prompt left open:
  - The flag is kept across the overflow reset (`resetAndRequestInit` / `cleanupMediaSource` do not clear it): the rebuilt SourceBuffer then begins on a keyframe fragment instead of a mid-GOP one. The server sends one keyframe fragment about every second (10 fragments), so the wait after a reset is short. `stop()` clears the flag and `consecutiveDrops` so the same player started again takes any fragment.
  - An empty chunk (byteLength 0) is returned from before it can end the wait or reset the drop count, and it is not acked. Before, it reset the drop count.
- Consequence to know about: waiting for a keyframe now counts toward the 15-drop limit. With a keyframe about every 10 fragments, a full-queue drop followed by the wait for the next keyframe is normally 10 drops or fewer, below the limit; a longer wait (a server that sends no keyframe flag) ends in the fresh-init request, as a stall should. Audio-only streams carry `keyframeStart: false` on every fragment, but the server never starts a viewer without a keyframe fragment either (`state.started` in `deliverFallbackFragment`), so no such viewer receives fragments.
