TASK-067 (C-8759928f0f6e): fixed on lane/fmp4.

- src/lib/fmp4RelayPlayer.js: `userPaused` is set by the video element's 'pause' event and cleared by its 'play' event. The listeners are added in `start()` (for the whole run, not per MediaSource, so a pause or play that comes while the player rebuilds is not missed) and removed in `stop()`, which also clears the flag. A 'pause' with `videoElement.ended` true is ignored (playback reaching the end raises one too; `cleanupMediaSource` ends the stream on every rebuild, so without the guard a rebuild could mark a viewer who never paused as paused).
- `liveSync` returns early while `userPaused` is set (after resetting its stall counters), so it does not call play(). It also does not seek or change the playback rate: the prompt only names play(), but with the seek left in, a paused picture would jump to the live edge every couple of seconds (ahead > target + 1.5 s), which is no pause. The first tick after the viewer plays does the normal live-edge correction (Q-004 default: jump to live).
- `maybeStartPlayback` (first start and start after a rebuild) still seeks to the cushion but only calls play() when the viewer is not paused. A refused play() (autoplay policy) and a stall raise no 'pause' event, so they are still resumed.
- Where the prompt differs from the code:
  - Step 1 (a flag around the player's own pause() calls): the player never calls pause(), so there is nothing to flag; every 'pause' event is the viewer's (or the browser's on their behalf). A comment says so.
  - Step 3 (a pause/resume API used by WatchView): the player has none, and WatchView controls the element directly. WatchView.jsx is unchanged. Its own `userPausedRef` (onPlay/onPause on the video element) serves the WebM path only and was not touched.
- Left open, for the owner:
  - A pause by the browser or OS (media keys, a phone call, a mobile browser pausing a background tab) fires the same 'pause' event as a click and counts as the viewer's. The old behaviour resumed those at once; now the viewer presses play (the same as WatchView's own `onPause` already treats them for the WebM path).
  - While paused, media keeps being appended past the playhead and nothing trims it (trimBuffer only removes behind the playhead). A very long pause ends in QuotaExceededError retries, then a full queue and the existing queue-overflow rebuild, after which the player waits paused for the viewer. Previously a pause lasted at most one tick, so this path was never reached by a pause.
