- The prompt's read_first lists tests/hostRecovery.test.js, which did not exist; TASK-070 adds its shouldTeardownAfterStartFailure to src/lib/hostRecovery.mjs and can add its tests to the same file.
- The prompt's step 2 offers "stopObsStream directly or a mode override on stopObsIngest"; the override was chosen so that an open control channel, if there is one, is used first and only one stop is sent.
- Constants (src/lib/hostRecovery.mjs): window 25 s from the first attempt, 5 s per attempt (connect and ack each), at most 10 attempts, pauses 0.5/1/2/4 s. The server holds the room HOST_RECONNECT_GRACE_MS (30 s) from the old page's disconnect, so the numbers fit that default; with a shorter operator-set grace the last attempts get "room not found" (terminal) and end the session, which is the same outcome as before.
- Each attempt is one socketRequest with maxAttempts 1, so socketRequest's own second attempt for reclaim-host (TASK-077) is not stacked on the loop's.
- Exhausted transient failures end the session with the text "Could not reconnect to the previous room in time. Create a new room to continue." (a terminal rejection keeps the server's reason). New user-visible string.
- Not asked, added on purpose: the retries make the stored reclaim last up to 25 s instead of failing in at most a couple of request timeouts, and during that time the page is idle with Start Sharing available (the host sees no "reconnecting" status; none was added). If the host starts a room of their own in that window, the retry loop stops (startGuard.activeOperation !== null, checked before each attempt and before each pause) and a final failure only forgets the stored record if it still names the old room; it does not call terminateHostSession and does not stop OBS, since the new session and OBS's single output may belong to the new room. The result of a request already in flight when the host starts a room is still honoured as before (a late success would still overwrite the new session's state; that ordering problem was already noted by TASK-063 and is not fixed here).
- An in-app unmount of the host view clears the stored record through cleanup() by design, so a navigation away during retries leaves no record; only a page unload (pagehide with recovery) keeps it.
- The media-flow spec hard-codes port 3210 in its loopback-proxy setup, so tests that use browser.newContext() reach whatever server is on 3210 (another lane's) when the config's port differs; the 3 reload/route tests then fail on the unchanged code too. The 12 scenarios were run as a port-shifted temporary copy (not committed), as TASK-063 did.
